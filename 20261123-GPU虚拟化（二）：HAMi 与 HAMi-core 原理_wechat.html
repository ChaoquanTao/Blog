01承接上篇：在 Kubernetes 里，我们需要怎样的 GPU 切分？

上一篇我们聊了 NVIDIA MIG。它像给大平层砌承重墙一样，在硬件层面把一张大 GPU 物理隔开，虚拟化调度层几乎零开销、隔离性拉满。但一旦把视角放到真实的 Kubernetes 集群里，MIG 的短板就非常明显了：

存量卡不支持：集群里大量卡是 T4、V100、A10、L40，芯片里压根没有 MIG 硬件电路；

粒度不够细：业务需求五花八门——有人只要 2GB 显存跑 Embedding，有人要 12GB 显存 + 30% 算力跑小模型，固定规格的 MIG 切不出这么细的粒度；

静态规格碎片：整张卡明明空着，却因为预切规格对不上导致 Pod 一直 Pending。

于是问题变成了：能不能不依赖特殊硬件，在软件层面把任意一张 GPU 按需切分，并且无缝融入 Kubernetes 的调度体系？

答案就是 CNCF 开源项目 HAMi（Heterogeneous AI Computing Virtualization Middleware，异构 AI 算力虚拟化中间件）以及它最核心的底层组件 HAMi-core。

02理清架构：HAMi 和 HAMi-core 是什么关系？

很多人容易把 HAMi 和 HAMi-core 混为一谈，其实它们是整体与底层核心模块的关系：

HAMi —— 集群侧的“大管家”

整套 Kubernetes 异构算力管理平台（Go 语言为主），负责集群里的资源上报、调度选卡、账本管理与容器注入。

HAMi-core —— 容器内的“门禁”

HAMi 旗下的底层 C/C++ 核心库（独立仓库，编译产物即 libvgpu.so），专门通过 LD_PRELOAD 实现 NVIDIA GPU 的软件层隔离。

理清整体架构后，最核心的问题就落到了 libvgpu.so 身上：它是如何在不改一行 PyTorch 代码的前提下，拦住容器里的 CUDA 调用的？这就需要了解两个经典的 Linux 底层概念：动态链接器（ld.so）和 LD_PRELOAD。

03底层原理：动态链接器（ld.so）与 LD_PRELOAD

3.1 什么是动态链接器（ld.so）？

我们平时写的程序（比如 python），会调用大量公共函数——比如打印日志用的 printf、申请内存用的 malloc，或者操作显卡用的 CUDA 函数 cuMemAlloc。编译程序时，处理公共库有两种方式：

静态链接：编译时把所有依赖库代码全部复制打包进可执行文件。独立性强，但体积巨大，且多个进程无法共享同一份库代码。

动态链接（Linux 默认方式）：编译时不复制库代码，只在可执行文件里留一张“依赖清单”（需要哪些 .so 共享库、要调用哪些函数名），等程序真正启动时再去加载系统里的 .so 文件。

正因为库代码不在可执行文件里，程序运行前必须有一个“搬运工 + 接线员”先把库装进来——这就是 动态链接器（ld.so）（在 64 位 x86 Linux 上，它通常是 /lib64/ld-linux-x86-64.so.2）。当你敲下 python train.py 时，幕后发生了 4 步：

1内核先唤醒 ld.so：Linux 内核发现程序是动态链接的，不会直接运行它的 main()，而是先把 ld.so 跑起来。

2加载 .so 库：ld.so 读取依赖清单（用 ldd /bin/ls 可查看），按顺序把 libc.so、libcuda.so 等映射到内存。日常遇到的 cannot open shared object file 就是这一步报的错。

3符号解析（接线）：程序只写了“我要调 cuMemAlloc”，ld.so 按加载顺序查表，把找到的第一个同名函数的内存地址填进程序里。

4交出控制权：线全部接好后，ld.so 跳转到程序的 main()，程序正式开始执行。

3.2 什么是 LD_PRELOAD？

注意上面第 3 步里极其关键的规则：ld.so 查找函数地址时是“先到先得”的。而 LD_PRELOAD 就是 Linux 动态链接器提供的一个环境变量（也可通过 /etc/ld.so.preload 全局配置），它的机制很直接：

强制让 ld.so 在加载任何其他共享库之前，先把我指定的 .so 库排在最前面加载。

假设程序原本要调用官方 libcuda.so 里的 cuMemAlloc() 申请显存。现在 HAMi-core 编译出的 libvgpu.so 里也定义一个一模一样名字的 cuMemAlloc()，并在容器启动时设置 LD_PRELOAD=/path/to/libvgpu.so。接线时，ld.so 第一个找到的就是 libvgpu.so 里的函数。

// 调用链路对比：普通调用 vs LD_PRELOAD 拦截

正常情况（无 LD_PRELOAD）

PyTorch → 官方 libcuda.so → GPU 驱动分配显存

设置 LD_PRELOAD=libvgpu.so 后

1. PyTorch 调用 cuMemAlloc() → 先被 libvgpu.so 拦截并核对显存配额

↓ 分支判定

超过配额：直接返回 CUDA OOM 错误，保护同卡其他容器

未超配额：通过 dlsym(RTLD_NEXT) 转发给官方 libcuda.so → 正常分配显存

打个比方，这就像在电话线路中间串了一个接线员：程序以为自己在直接给 CUDA 打电话，其实请求先经过了 libvgpu.so 检查——合规就转接给真正的 CUDA，超标就直接挂断。而且整个过程对业务代码完全透明、零侵入，PyTorch、TensorFlow 和业务镜像一行代码都不用改。

第 1 步：Pod 按需申请资源

开发者不再只写 nvidia.com/gpu: 1 独占整卡，而是可以同时声明所需的显存和算力配额（不同接入方式资源名略有差异，以下是 HAMi / Volcano 的典型写法）：

// Pod 资源配额声明示例

resources: limits: nvidia.com/gpu: 1 # 1 块 vGPU（Volcano 下为 volcano.sh/vgpu-number） nvidia.com/gpumem: 10000 # 显存上限 10000 MiB（约 10GB） nvidia.com/gpucores: 20 # 算力上限 20%

第 2 步：调度器记账与选卡

调度器手里维护着集群里每一张物理 GPU 的实时账本：给 Pod A 分配 GPU-0 后，账本扣减为剩余 70GB / 80%；紧接着 Pod B 来了，账本依然够用，于是也调度到同一张物理 GPU-0，扣减为 55GB / 50%，并将选中的物理卡 UUID 写进 Pod Annotation。

第 3 步：Device Plugin 注入“门禁”

容器启动前，kubelet 调用节点上的 HAMi Device Plugin：读取 Pod Annotation 挂载对应的物理 GPU-0；最关键的一步是把宿主机上的 libvgpu.so 挂载进容器，通过 LD_PRELOAD（或 /etc/ld.so.preload）使其生效，并注入环境变量告知配额。

第 4 步：容器运行期，HAMi-core 接管三大核心能力

显存硬限制

拦截 cuMemAlloc 等分配与释放 API，在容器内通过共享内存账本统计所有进程的累计显存用量。一旦 Pod A 申请超 10GB，即使物理卡还剩 55GB，也会直接返回 OOM，保护同卡上的 Pod B。

算力配额控制

拦截 cuLaunchKernel 等核函数提交调用。在短时间窗口内采样当前容器的算力占比，一旦超过 20%，就在 CPU 侧让后续 Kernel 提交短暂 sleep 排队，把平均算力平滑压在 20% 左右。

视图虚拟化

拦截 NVML 查询接口。在 Pod A 里敲 nvidia-smi，看到的显存总量就是 10000 MiB 而非整卡 80GB，让容器觉得自己真的独占了一张 10GB 小卡。

05没有银弹：HAMi-core 的局限性

看完上面的原理，HAMi-core 听起来几乎完美：不挑卡型、按需切分、业务代码零侵入。但它的优势来自基于 LD_PRELOAD 的用户态 API 劫持，短板也同样源于此：

局限 1：软隔离，防不住故障波及，也挡不住“噪声邻居”

同卡容器共享同一张物理 GPU 与宿主机驱动：一旦某容器触发严重驱动或硬件异常，同卡其他容器可能被连带牵连；同时 L2 缓存和显存带宽未切分，邻居密集读写仍会影响速度。此外，用户态拦截在权限管控不严时存在绕过风险，不适合完全不可信的公有云强隔离场景。

局限 2：算力限流是“事后拉平”，容易带来延迟抖动

无法像硬件那样把算力切死，也不能打断正在执行的计算任务，只能靠时间窗口采样 + CPU 侧短暂 sleep 拉平平均算力。若某任务提交了耗时很长的大计算，会先吃满整卡再通过后续排队“还债”，对延迟敏感的在线推理容易出现耗时抖动。

局限 3：显存统计存在误差，需要预留缓冲余量

API 拦截主要统计业务主动申请的显存，驱动为每个进程维护的上下文等底层开销很难 100% 精确统计。生产中通常需要给物理卡预留一点显存余量，避免“账本没超、物理卡却 OOM”。

局限 4：强依赖动态链接与 CUDA 生态，有一定兼容性成本

静态编译的程序会直接绕过 LD_PRELOAD，非 CUDA 生态调用也管不到；此外，当 CUDA 或 PyTorch 升级引入新的内存/计算接口时，HAMi-core 也需要同步跟进适配。

一句话概括：HAMi-core 是用“隔离强度、延迟稳定性，以及一定的版本适配成本”，换取了“不挑卡型、任意细粒度切分、极高集群利用率”。

06总结

两种方案各有取舍：追求硬件强隔离选 MIG，追求灵活性与利用率选软件 vGPU。而像 HAMi 这样的调度框架，同时支持 HAMi-core 软件切分与 Dynamic MIG，一定程度上已经覆盖了两种场景。

另一方面，用户态拦截不可避免会带来性能损耗、限流抖动与绕过风险，这也是阿里云 cGPU、腾讯云 qGPU 等云厂商选择自研内核态拦截方案的原因。
