镜像加速技术选型：eStargz vs Nydus

几十 GB 的 AI 镜像，Pod 冷启动绝大部分时间卡在 Pulling → Pulled。两条"惰性拉取"路线的原理、架构与实测对比。

Lazy PullingeStargz Nydus / RAFScontainerdEROFS

00一句话结论

惰性拉取的核心思想：容器不必等镜像下载完，按需只取真正被访问到的数据块即可启动。

路线 A · eStargz

在 OCI tar.gz 上做"可随机读"的最小扩展。改动小、100% 兼容现有 registry 与运行时；但去重能力、随机小文件 IO、生态都弱一些。

路线 B · Nydus

为镜像加速专门设计的 RAFS 格式（v6 与 EROFS 兼容）。支持 chunk 级去重、内核态挂载、P2P 分发。能力更强，但引入专用运行时与内核版本要求。

当前状态：POC，尚未拍板 两条路线都做过实现试跑，倾向 Nydus 但未决定采用。代价要认清：Nydus 多一个 nydusd 常驻进程、节点侧 containerd 改造、产物非原生 OCI。收益需在灰度节点实测，不要照搬社区数字。

01OCI 镜像为什么慢

标准镜像每层是一个 gzip 压缩的 tar 包。启动前 containerd 必须拉取全部压缩包，再解压落盘展开成 rootfs。两个致命属性：

  • 全量 — 哪怕启动只用到 5% 的文件，也要先下载并解压 100%
  • 串行阻塞 — gzip 流不可随机寻址、tar 无目录索引，只能整包顺序解压

02惰性拉取的通用原理

两条路线建立在同一组思想上，区别只在于用什么格式实现"可随机读"，以及按需加载发生在用户态还是内核态。

能力作用
可随机读的镜像格式镜像内每个文件 / 数据块能被单独定位、单独取回，不必顺序解压整层
元数据与数据分离先只拉一份"目录"，就能把 rootfs 挂起来
按需加载 on-demand容器真正 read() 到某文件时，才通过 HTTP Range 回源对应数据块并缓存
预取 prefetch对启动关键路径的文件提前批量拉取，减少运行期抖动
snapshotter 插件containerd 外置 snapshotter，"挂一个懒加载文件系统"当 rootfs，而非解压落盘

03eStargz：给 tar.gz 打补丁

格式：seekable tar.gz + TOC

源自 Google CRFS 的 stargz（"seekable tar.gz"），由 containerd 的 stargz-snapshotter 扩展。巧妙之处是在不破坏 OCI tar.gz 兼容性的前提下让它可随机读：把每个文件（大文件再切 chunk）各自压成一个独立 gzip 流拼接起来——多个 gzip 流拼接仍是合法 gzip——末尾追加 TOC 索引记录每个文件的偏移与长度。

最大优点：零生态改造 产物仍是标准 tar.gz 层，能推到任何标准 registry（只需支持 HTTP Range）；不认识 eStargz 的旧运行时把 TOC 当普通文件忽略即可，退化为普通全量拉取——向后完全兼容。

运行时：一层一个 FUSE 挂载

节点侧运行 stargz-snapshotter，读 TOC 后用 FUSE 挂文件系统当 rootfs；容器读文件触发 FUSE 回调 → 按偏移发 Range → 解压返回。

设计层面的短板

  • 按层挂载 — N 层 → N 个 FUSE 挂载 + overlayfs 叠加，故障域和查找开销都随层数增长
  • 几乎无去重 — 只有 OCI 原生的整层 blob-digest 去重，连镜像内相同内容都不去重（同一文件出现两次就存两份），更无跨镜像 chunk 去重
  • 用户态 + gzip 解压 — 命中和回源都走用户态 FUSE，随机小文件密集访问开销偏高
  • 压缩受限 gzip — 格式即 seekable tar.gz，用不了 zstd
  • 元数据用户态解析 — TOC 是 JSON，大镜像索引本身也不小
实测踩坑：大镜像冷启动懒加载失败（并发惊群） 8.9 GiB 的 vLLM 镜像清缓存后首次冷启动，偶发回退到全量拉取。原因：stargz-snapshotter 挂载时会并发预解析 manifest 里所有邻居层，冷启动时 token 缓存为空，几十个并发请求几乎同时撞 Bearer 401、各自去取 token，形成鉴权惊群（cache stampede）；个别层 resolve 超时即导致整镜像退回全量拉取。
Nydus 只有一份 bootstrap、没有邻居层可预解析，从根上就没有这个扇出。

04Nydus：重新设计一套格式

CNCF Dragonfly 的子项目，不是"给 tar.gz 打补丁"，而是重新设计了面向镜像加速的只读文件系统格式 RAFS（Registry Acceleration File System），配套 nydusd 守护进程、nydus-snapshotter、nydusify 转换器与 Dragonfly P2P 分发。

核心数据模型：bootstrap + blobs，chunk 化

RAFS v5 → v6：从用户态 FUSE 到内核态 EROFS

RAFS v5RAFS v6（当前主线）
元数据解析用户态 nydusd 解析私有格式内核态：与 in-kernel EROFS 兼容
挂载方式FUSEEROFS（可走 fscache）/ 也支持 FUSE
随机 IO每次访问都要用户态往返命中缓存直接内核态返回
内核要求无EROFS 块设备需 ≥ 5.16；over fscache 需 ≥ 5.19
页缓存主要由各层 FUSE 挂载维护fscache 后端更利于内核侧复用

EROFS over fscache 命中时数据直接由内核 fscache 提供，只有 cache miss 才唤醒 nydusd 回源——省掉系统调用与上下文切换。

运行时组件与数据流

  • nydus-snapshotter — containerd 外置 snapshotter（proxy_plugins 注册），按镜像拉起 nydusd 并挂载；支持 FUSE / fscache(EROFS) / virtiofs 后端
  • nydusd — 核心守护进程：挂载 RAFS、解析 bootstrap、处理 on-demand chunk 回源与本地缓存
  • nydusify — 转换器：pull OCI → 转 Nydus → push 回 registry，并能 check 校验
  • Dragonfly P2P（可选） — 节点间 P2P 分发 blob，避免大规模集群回源打爆 registry
需要注意 blobcache 没有容量淘汰机制，依赖 kubelet GC：kubelet 负责"选择并触发删除未使用镜像"，containerd / nydus-snapshotter 负责按引用关系回收 snapshot 和整个 blobcache。目前缺少对活跃镜像做 chunk 级容量淘汰的能力。

05启动全流程对比

例子：一个 ~20 GB、约 40 层的 vLLM 推理镜像，启动阶段实际只 import 了其中几百 MB 的 Python / CUDA 库。

步骤eStargz · 按层懒加载Nydus · 合并挂载懒加载
① 拉索引拉各层 manifest + 每层 TOC（KB~MB，不含数据）拉一份 bootstrap（整镜像合并元数据）
② 挂 rootfs每层各建 remote snapshot、各挂一个 FUSE，用 overlayfs 叠 ~40 层拉起一个 nydusd、单个合并挂载直接当 rootfs
③ 启动容器启动，几乎没下载文件数据
④ 首次 read命中该文件所在层 FUSE → 查该层 TOC → 一个 Range 拉回该文件 gzip 流 → gzip 解压page cache miss → 定位 chunk → Range 拉回目标 chunk（必要时合并相邻 chunk）→ 解压 → 写 blobcache + 页缓存
⑤ 缓存单位按 layer blob 的字节范围；获取单位通常对应单个文件的 gzip 数据范围按 RAFS chunk，必要时合并相邻 chunk 预读
⑥ 内容复用相同 OCI layer blob 可复用缓存；不做跨文件 / 跨层去重同一 blob/chunk 引用可复用；跨镜像共享取决于 chunk-dict 与运行时配置
⑦ 未访问未访问的层与文件永不下载未访问的 chunk 永不下载
五处关键差异 挂 rootfs（N 挂载 + overlayfs vs 1 合并挂载）· 回源单位（一段 gzip 流 vs chunk 可合并预读）· 解压与命中路径（gzip + 用户态 FUSE vs zstd + 可选内核态）· 缓存定位（layer 字节范围 vs RAFS chunk）· 内容复用能力（layer blob 级 vs chunk 级）

拉取 + 启动：298 s → 13 s，约 22× 这是惰性拉取最直观的收益，且镜像越大优势越明显。
但运行期首读明显变慢 ② shell→python 从 1.3 s 涨到 16~18 s，⑥ 重点读 ~28 GB 从 42~46 s 涨到 88~96 s。原因是"没在 pull 阶段付的成本，挪到了首次 read 阶段付"——冷 blobcache 下每次 miss 都要 Range 回源 + 解压。缓存热起来后差距会收敛（对比轮次 2 的 ⑦：oci 20.5 s vs nydus 54.5 s，比轮次 1 都有下降）。

社区与厂商公开材料的定性结论（数字仅作量级参考，不要直接对外引用为我们的结果）：冷启动"分钟级降到秒级"；fscache 模式顺序/随机读接近 loop device、优于 FUSE；配合 Dragonfly P2P 生产网络延迟可降 80%+。

08取舍小结

选 eStargz 的理由

  • 零生态改造，产物就是标准 OCI 层
  • 旧运行时自动退化，不会"上不去下不来"
  • 只多一个进程，改造成本最低

选 Nydus 的理由

  • chunk 级去重，镜像多、层数多时优势明显
  • 单挂载点，无 overlayfs 叠层与惊群问题
  • v6 内核态路径 + zstd + Dragonfly P2P
