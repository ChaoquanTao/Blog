训练加速之镜像懒加载（一）：eStargz

30 GB 训练镜像，启动真正读到的只有 ~2 GB。为什么不能只传这部分？

OCIeStargz containerdLazy Pulling

01问题

6.4%
容器启动过程中平均只读取了镜像内容的 6.4%
— Slacker, USENIX FAST '16（威斯康辛大学 Harter 团队实测）
  • 30 GB 训练镜像 → 启动实际读到 ~2 GB
  • 其余 28 GB：用不到的 GPU 架构 kernel、没 import 的算子、debug symbols、locale、文档
  • 200 节点发版：制品库带宽打满、GPU 空转 90 分钟、每次蒸发 900 美元
那为什么没人做按需加载？OCI 镜像格式本身不允许。

02卡在哪：tar.gz 天生反随机访问

  • OCI 规定每层 mediaType = tar+gzip，digest 对整层 blob 计算 → 层是分发和校验的最小单元
  • gzip 用 DEFLATE（滑动窗口 + Huffman），每字节解码依赖前文字典 → 不能从中间开始解压
  • 后果：HTTP Range 拉不出可用数据，无论用不用，整层必须完整下载 + 完整解压
两条路 ① 换掉 tar.gz，用天生可随机访问的新格式 → Nydus（下篇）
② 不换，让 tar.gz 变得可随机访问且保持格式合法 → eStargz

03eStargz：让 tar.gz 变 seekable

核心洞察：多个独立 gzip 流首尾拼接，本身仍是一个合法的 gzip 文件。
→ 把 tar 里每个文件单独 gzip，再拼起来，结果仍是合法 .tar.gz。

原版（不可 seek）  gzip( [hdr_A][A][hdr_B][B][hdr_C][C] )
                   └────── 一整个连续的 gzip 流 ──────┘

eStargz（可 seek） gzip([hdr_A][A]) ‖ gzip([hdr_B][B]) ‖ gzip([hdr_C][C]) ‖ gzip(TOC) ‖ footer
  • 启动只需两次小请求：Range: bytes=-51 取 footer → 按偏移取 TOC（几十 KB）
  • 之后按文件单独 Range 拉取、本地解压
为什么能落地 对不知情的客户端完全透明（普通 pull 得到的还是原来的层）· 制品库无需任何改造

04Prefetch：按需 ≠ 够快

100 个启动期文件 × 30 ms 往返 = 3 秒串行阻塞。pull 秒完成，容器却要 5 秒才能服务。
极致按需 = 极致往返次数，两者天然对抗。

                     landmark
                        ↓
┌──────────────────┬────┬──────────────────────────────────┐
│ 启动期文件       │ ✦  │ 其他文件（按需）                 │
│ 物理上连续的区域 │    │ 真的用到了再单文件 Range 取      │
└──────────────────┴────┴──────────────────────────────────┘
↑──────────────────↑
  prefetch zone：用一个大 Range 请求整段拉下来
  • 构建时 profiling（ctr-remote optimize）记录启动期访问的文件
  • 重排 tar，把这些文件挪到最前面物理连续，中间插 .prefetch.landmark 标边界
  • 100 次往返 → 1 次大 Range 请求

05运行时：Stargz Snapshotter

containerd 的 snapshotter 插件，替换默认 overlayfs 的"下载 + 解压"动作：挂 FUSE 把 layer 虚拟成目录树，容器 read() 时拦截 → 查 TOC → HTTP Range 回源 → 解压 → 本地缓存。对容器进程完全透明。

方案pull 阶段实际传输耗时
传统 pull整层 30 GB~90 秒（3 Gbps）
Stargz Snapshotterfooter + TOC ≈ 几百 KB< 100 ms
端到端从任务下发到容器就绪：分钟级 → 秒级。 （走 containerd 生态：ctr / nerdctl / K8s；Docker 引擎默认 pull 不经过 snapshotter）

06代价：没有银弹

压缩率变差

每文件各起一个 gzip 流，丢掉跨文件共享字典。site-packages 这类海量小 .py 膨胀最明显。

去重能力弱

寻址单位仍是整层 blob。PyTorch 2.3/2.4 两个 3 GB CUDA 层内容 99% 重叠，也得存两份。

一层一个 FUSE 挂载

28 层镜像 = 28 个挂载点，随「镜像数 × 层数」线性增长；每个都是独立故障单元，任一层挂 = 整个 rootfs unavailable。

resolve 超时静默回退

每层 resolve 有硬编码 30 秒 timeout，超时后 containerd 静默退回全量拉取，收益直接清零。

07什么时候不该用

  • 大部分文件都会被用到 — 如 CI 构建镜像，没什么可"懒"的，FUSE 开销反而拖慢 IO
  • 模型权重占主体 — 30 GB 里 25 GB 是 .safetensors，启动就要全量 load 到显存。
    更好的方案：把权重从镜像剥出来，用模型服务或 blob storage 管
  • 制品库高可用没保障 — 传统 pull 下载完就切断依赖；懒加载要求制品库 24/7 在线

08小结

  • 启动只读 6.4%，但 tar.gz 天生反随机访问
  • eStargz = 拼接 gzip 流 + TOC 索引，保持 OCI 兼容的前提下实现按需拉取
  • Prefetch 化解"按需"与"往返次数"的对抗；Stargz Snapshotter 把这套接进 containerd
  • 但雕花终究是雕花：压缩率、去重、挂载点膨胀、超时回退
