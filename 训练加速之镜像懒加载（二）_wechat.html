镜像加速系列 · 第二篇

训练加速之镜像懒加载（二）

Nydus 把压缩和寻址降到 chunk
把叠加升到整个镜像
以及为此付出的代价

本文讲什么

上一篇讲了 eStargz——在 OCI 的旧格式里雕花，换来零生态改造。这一篇讲 Nydus：它重新设计了镜像格式，拿到了更彻底的能力，也背上了更重的运行时依赖。最后一节跳出技术，聊聊为什么 OCI 被吐槽十年仍是主流，以及同一项技术为什么在训练平台可有可无、在 serverless 却是生死线。

01

在旧格式里雕花，要付出什么代价

上一篇讲到，eStargz 可以让镜像不必全部下载完就启动，从观测结果看，pull 时间几乎降到了零。但这并不是免费的：它有三笔绕不开的结构性代价——压缩率变差、去重能力弱、一层对应一个 FUSE 挂载点；此外，还有 resolve 超时后静默退回全量拉取的运行时风险。

这几个问题看似互不相关，根源却是同一个：

压缩率变差

一层内部共用一个 gzip 字典。想让单个文件能被独立解压，就必须把这个字典拆掉。

去重能力弱

层 blob 的 digest 就是寻址单位。两层只要差一个字节就是两个不同对象，制品库和本地缓存都没有更细的粒度可用。

N 层 N 个挂载点

层是叠加单位。容器 rootfs 由 overlayfs 把每层 lowerdir 摞起来，镜像有多少层就得挂多少次。

三个症状，一个病根：在 OCI 的世界里，“层（Layer）”同时承担了三份工作——压缩、寻址和叠加。

可以把它想成一家仓库：货物按“整层”打包，仓库按“整层”编号，出库时还要按“整层”一层层摞起来。只要其中一个环节想改得更细，另外两个环节就会跟着受影响。

eStargz 没有推翻这套模型，而是在层内部增加索引和可随机读取能力。好处是兼容性极佳：旧运行时不认识 eStargz，也能把它当成普通 OCI 镜像使用。代价是，它能优化到什么程度，仍然受“层”这个基本单位限制。

上一篇把这条路线称为“在旧格式里雕花”。这不是贬义，而是一种清醒的工程取舍：少实现一部分高级功能，让现有工具尽量无须修改。

但如果允许你把这三顶帽子摘下来重新分配呢？

“

这正是本文主角 Nydus 的思路：把压缩和寻址的单位从 layer 缩小到 chunk，把叠加的单位从 layer 放大到整个镜像。

这样一来，“层”仍然可以存在于镜像的构建和分发语义中，却不再主导运行时的数据读取。下面先拆开看它是怎么做到的，再算清楚为此付出的代价。

02

Nydus：把“目录”和“货物”分开

Nydus 是 CNCF Dragonfly 项目下的子项目，可以先把它拆成两部分：

RAFS（Registry Acceleration File System）

一套专为镜像加速设计的只读文件系统格式。

nydusd

一个根据文件访问请求，从远端按需取回数据的守护进程。

如果把镜像比作一座仓库，RAFS 负责规定“目录怎么写、货物怎么分块摆放”，nydusd 则像仓库管理员：先拿到目录，等容器真正要用某件货物时，再去对应位置把那一块取回来。

图中 ①～④ 是控制面：containerd 把快照管理交给 nydus-snapshotter；snapshotter 落地 bootstrap、启动 nydusd；nydusd 挂载出整个镜像的只读视图；最后，overlayfs 在上面叠加一个可写层，再交给 runc。

核心判断

这里最值得注意的是：lowerdir 只有一个，与镜像原本有多少层无关。图中的 ⑤～⑦ 是数据面，只有当容器运行后真正读取文件时才会发生。

两条启动路径对照着看：

// 传统 OCI

逐层下载 → 逐层解压落盘 → overlayfs 叠 rootfs → 启动

// Nydus

拉 bootstrap（几 MB） → 挂载 RAFS → 启动 → 运行期按需取 chunk

传统 OCI 把大量 I/O 前置到启动阶段；Nydus 则把文件内容的下载延后到真正访问它的那一刻。

Nydus 并没有让网络变快，它只是让容器启动不再等待所有镜像数据下载完成。省下来的工作并未消失，只是被推迟了——到了第 06 节，这会变成一笔必须偿还的账。

03

RAFS：一棵树 + 一堆块

RAFS 的核心设计：把“文件在哪里”和“文件内容是什么”分开保存，而且目录描述的是整个镜像，而不是某一层。

bootstrap · 目录册

记录完整的文件系统结构，以及每个文件的数据在哪里。

blobs · 货架

真正存放文件内容的地方，内容会被切成许多 chunk 保存。

3.1　bootstrap：整个镜像只有一棵树

bootstrap 保存完整的文件系统元数据：目录结构、文件名、权限、属主、大小和时间戳。更关键的是，它还记录了一个文件由哪些 chunk 组成、每个 chunk 位于哪个 blob 的哪个偏移，并附带用于完整性校验的摘要。

“

bootstrap 中保存的，是所有镜像层合并之后的最终文件树。层与层之间的覆盖关系、whiteout（删除标记）和 opaque 目录，都已经在构建期处理完毕。

对比传统 OCI：一个 28 层的镜像，运行时需要由 overlayfs 把 28 个目录依次叠起来。查找一个文件时，可能要从最上层一路向下寻找，直到命中，或者确认它已被 whiteout 删除。

Nydus 把这项工作提前到了 nydusify 转换阶段。容器启动时拿到的已经是一棵合并完成、没有歧义的文件树。并不是运行时更擅长逐层查找，而是逐层合并这个问题，早在构建期就已经解决了。

为什么 pull 近乎瞬时

bootstrap 通常只有几 MB 到几十 MB，而它描述的镜像可能有几十 GB。所谓“拉取 Nydus 镜像”，主要只是先下载这份目录册，而不是把仓库里的全部货物搬到本地。

3.2　blobs：把文件切成可独立取回的小块

文件内容不再以“整层 tar 流”的形式保存，而是被切成定长 chunk（Native RAFS 常见大小为 1 MiB）。每个 chunk 都具备三个特征：

1

独立压缩：解压这一块时，不需要先解压前面的内容。
2

按内容寻址：身份由内容摘要决定，而不是由“属于哪一层、哪个文件”决定。
3

可单独取回：知道偏移和长度，一次 HTTP Range 请求即可获取。

这里很容易与 eStargz 混淆。eStargz 同样会切分数据：通常每个文件对应一个 gzip 流，大文件还会继续按 4 MiB 切块。但它切分的主要目的是让运行时能够 seek 到某个位置；一个块仍然通过“某个 layer 中的某段偏移”来定位。

Nydus 更进一步：chunk 是按内容寻址的。只要内容完全相同，无论它出现在哪个文件、哪一层，甚至哪个镜像里，都可以被识别为同一个 chunk。这正是后面实现细粒度去重的基础。

这种设计还带来一个额外好处：压缩算法不再被 tar.gz 格式限制。eStargz 为了保证产物整体仍是合法的 tar.gz，只能使用 gzip；RAFS 没有这层兼容包袱，可以选择 zstd 等算法。

TOC 只知道某一层里有什么，bootstrap 则知道整个镜像最终长什么样。

后面谈到的所有差异——能否跨层去重、rootfs 需要几个挂载点、缓存按什么粒度复用——都可以追溯到这里。

工程细节 · RAFS 的两条挂载形态

RAFS v5 使用私有元数据格式，只能由 nydusd 在用户态解析，因此需要经过 FUSE。RAFS v6 的元数据布局与内核中的 EROFS 兼容，可由内核直接解析；本地没有所需数据时，再通过 fscache 从远端读取。缓存中已有数据时，请求不必反复穿越用户态，随机读取小文件所经过的步骤会明显减少。

代价是，使用 fscache 要求内核版本不低于 5.19；旧内核只能退回 FUSE 模式。这个版本要求会在第 06 节再次出现。

04

去重：把上一篇那个 3 GB 的例子算完

假设团队同时维护 PyTorch 2.3 和 2.4 两个训练镜像。它们各有一个 3 GB 的 CUDA 层，内容有 99% 相同。

在 eStargz 和标准 OCI 的模型里，只要两个层有一个字节不同，最终 digest 就不同。制品库和节点缓存只能把它们视为两个独立对象，结果就是：两个 3 GB 的层都要完整保存，即使其中几百 MB 的 libcudnn.so 一模一样。更进一步，即使重复内容出现在同一个镜像的不同层里，层模型也无法自动识别。

而 Nydus 以内容摘要标识 chunk，去重的粒度从“整层”缩小到了“数据块”，答案因此发生了变化。

4.1　镜像内去重：自动的

nydusify 转换镜像时，内容相同的 chunk 只需保存一份；bootstrap 中的多个文件位置可以共同引用它。这种镜像内部的去重不需要额外配置。

训练镜像中的重复内容往往比想象中更多：多阶段构建遗留的重复依赖、被 pip install 到不同虚拟环境中的同一批 wheel、在多个层中反复复制的模型配置文件……在层模型中，它们是“不同层里的不同副本”；在 chunk 模型中，相同部分可以指向同一份数据。

4.2　跨镜像去重：要配

跨镜像共享则不是自动获得的，它依赖 chunk-dict。转换新镜像时，需要指定一个参考镜像——通常是团队统一维护的基础镜像。nydusify 会优先复用字典中已经存在的 chunk，只有找不到时才写入新数据。

使用相同基础环境的镜像越多，节省的空间和网络流量越多。如果 10 个训练镜像都使用同一套 CUDA / cuDNN，理想情况下就不必另外保存和下载 9 份相同的 chunk。

此处插入图片

nydus_dedup.png

去重粒度对比：层模型存两份，chunk 模型只存共享数据加差异

左边是层模型：两个 CUDA 层内容 99% 相同，但 digest 不同，于是各存一份。右边是 chunk 模型：镜像 A 内部两个内容相同的文件指向同一批 chunk，这一步不需要配置；镜像 B 转换时带上 chunk-dict，libcudnn.so 直接复用 A 已有的 c1–c4，只有真正不同的 libtorch.so 才写入新的 d1、d2。

内容寻址也顺带提供了完整性校验的基础：每个 chunk 都有摘要，bootstrap 自身也有摘要，取回数据后可以逐块验证；在 RAFS v6 的 EROFS 路径上，特定部署形态（例如机密容器场景）还可以叠加 dm-verity 做块级校验。去重与校验看似是两种能力，底层依赖的却是同一件事：内容本身就是身份。

4.3　但这里有个诚实的边界

前置条件不在 Nydus

chunk 能否复用，取决于两次构建生成的字节是否完全一致。如果各团队各自维护基础镜像、基础镜像使用 latest、pip install 不锁版本，或者编译产物中混入时间戳和构建路径，那么两个“看起来一样”的 CUDA 层，实际字节可能并不相同，chunk-dict 的命中比例也会很低。

因此，想真正获得跨镜像去重收益，前置条件在构建流水线：统一基础镜像、锁定依赖版本，并尽量实现可复现构建。这件事的难度经常被低估——它不只是安装一个组件，还意味着要改变整个团队构建镜像的习惯。

05

数据面：容器跑起来之后

容器已经成功启动。但此时本地磁盘上除了几 MB 的 bootstrap，几乎没有真正的文件数据：大部分内容仍在远端。接下来，容器每一次读取尚未缓存的文件，才会触发真正的按需加载。

5.2　为什么“合并相邻 chunk”很重要

懒加载有一个天然矛盾：读取越精确，网络请求往往越零碎。极端情况下，串行读取 100 个小文件，可能意味着 100 次网络往返。即使实际下载的数据量不大，累计延迟也可能很可观。

Nydus 的 chunk 大小固定，并在 blob 中连续排布，这使合并请求更加容易。当 nydusd 发现多个待读取的 chunk 在物理位置上相邻时，可以把它们合并到一个 Range 请求中一次取回。顺序读取大文件时，还可以提前读取后续 chunk。

eStargz 每次从远端读取的，通常是“某个文件对应的 gzip 数据段”。不同文件在物理上是否相邻，取决于 tar 中的排列顺序，运行时很难按固定大小合并请求。

eStargz：物理重排

构建时先记录一次启动过程中访问了哪些文件，再把这些文件移动到 tar 流前部；运行时用一个大 Range 请求取回整段。文件顺序会固定在镜像中，因此记录结果是否准确非常关键。

Nydus：元数据指示

bootstrap 可以携带预取表，在转换时指定要预取的目录或路径模式。nydusd 启动后用独立线程在后台批量拉取。数据布局无须随预取策略一起调整，策略更容易修改。

5.3　和 eStargz 的关键差异

维度 eStargz Nydus
挂载模型 N 层 → N 个 FUSE 挂载 一个合并挂载，与层数无关
远端读取单位 某文件的一段 gzip 流 chunk，可合并相邻块
解压与命中路径 用户态 FUSE + gzip FUSE（v5）或内核态 EROFS + fscache（v6）；zstd
缓存定位 按 layer blob 的字节范围 按 chunk（内容寻址）
内容复用 仅整层 blob 级 chunk 级，跨镜像靠 chunk-dict
未访问的数据 永不下载 永不下载

表里藏着的共同风险

每一次缓存未命中，都可能把一次普通文件读取变成一次网络读取。数据面设计得越精细，运行期就越依赖缓存、网络和远端后端。下一节要算的，正是这笔账。

06

代价：省下的时间，最终要在哪里偿还

“

Nydus 的代价可以概括为：启动时没有完成的工作，需要在运行时继续完成。

传统 pull 像一次性付清：先完成下载、解压并占用磁盘，容器启动后，读取镜像文件通常不再依赖制品库。Nydus 更像分期付款：启动时只下载几 MB 的 bootstrap，相当于付了首付；剩余成本则在运行期间，随着一次次缓存 miss 陆续偿还。下面这些看似不同的问题，本质上都是同一件事的连锁反应。

6.1　首读放大：钱没消失，只是挪了位置

先看一组我们在概念验证阶段观察到的趋势。具体数据和镜像信息不便公开，这里只保留倍数关系；实际结果会受镜像、网络和后端影响，仍需先在少量测试节点上重新测量：

✓ 拉取 + 启动

Nydus 比原生 OCI 快约一个数量级，镜像越大，优势通常越明显。

✗ 冷 blobcache 下的密集首读

如果把镜像中的几十 GB 数据完整读取一遍，Nydus 反而可能慢约一倍。

≈ 缓存热起来之后

两者差距明显收敛。需要说明的是，上一条是刻意构造的全量顺序读；典型训练任务只会读到镜像中的一小部分，实际差距通常远小于此。

第二条看似反常，原因却很直接：pull 阶段没有完成的工作，被转移到了 read 阶段。每次缓存中没有所需数据，都可能需要通过 Range 请求从远端下载、校验摘要、解压，并写入 blobcache。原生 OCI 通常按层顺序、批量地完成下载和解压；懒加载则可能在应用读取过程中，以更随机、更零散、夹杂网络往返的方式补齐数据。总工作量没有凭空消失，执行方式反而可能更昂贵。

如果任务一启动就会读遍整个镜像，懒加载的大部分收益都会被抵消。

例如，一个推理服务启动后立刻要把 25 GB 权重全部加载到显存，这 25 GB 无论如何都必须读取，“懒”不起来。训练任务也要看具体行为：如果进入第一个 step 之前就必须扫描数据集并加载全部权重，那么只是把等待从 Kubernetes 的 Pulling 阶段挪到了应用初始化阶段，端到端时间未必会缩短。

6.2　运行时依赖变重

反直觉的生命周期

在“每容器一个 daemon”的模式下，nydusd 的生命周期绑定的是容器的 active snapshot，而不是镜像本身。容器执行 Prepare 时它被创建，执行 Remove 时才被销毁。（nydus-snapshotter 也支持 shared daemon 模式，以及 RAFS v6 + fscache 的形态；那时一个常驻进程服务多个容器，下面几个问题的表现也随之不同。）

强制删除 Pod 可能留下孤儿进程

kubectl delete --force 可能打断 snapshotter 的 Remove 流程，导致“卸载挂载点 + 停止 daemon”没有执行。它不会因为长时间空闲而自动退出，节点运行越久，残留进程可能越多。

只结束进程不能完成清理

如果启用了 daemon 恢复或重启策略，snapshotter 会根据自身记录重新拉起被结束的 daemon。要完整清理，需要从上游删除对应的 Pod 或 snapshot（crictl rmp / ctr snapshots rm），让 snapshotter 执行完整的销毁流程。

需要检查的环节更多

容器读取文件报错时，问题可能来自应用、overlayfs、nydusd、blobcache、远端存储，甚至过期凭据。每增加一个组件，就增加一类故障可能。

6.3　blobcache 不属于快照

另一个需要特别注意的问题是：blobcache 与快照拥有不同的生命周期。

删容器不会删缓存

随着节点运行过的镜像越来越多，缓存目录会持续增长，必须单独限制容量并制定清理规则。

daemon 还活着时手动删缓存很危险

文件虽然被 unlink，但文件描述符仍可能保持打开，nydusd 的内存状态和磁盘状态不再一致，容器侧可能出现 input/output error。

正确顺序是：先让相关 daemon 全部退出，再清理缓存。可惜在“半夜磁盘告警，先赶紧删点东西”的场景里，这条规则最容易被忽略。监控上至少要补充两个指标：blobcache 容量增长曲线和缓存命中率。

6.4　产物非原生 OCI：无法自动改用普通拉取

这是 Nydus 和 eStargz 之间最本质的工程差别。

✓ eStargz 有退路

产物仍是合法 OCI 层。不认识它的运行时会当作普通镜像全量拉取，即使 Pod 被调度到未安装组件的节点，通常也只是没有加速，容器仍可启动。

✗ Nydus 没有退路

转换后的数据层不能由普通 OCI 运行时直接解包，没有 Nydus 运行时支持的节点无法直接启动它。

这意味着：小规模试用时需要把节点分组并设置调度规则；制品库通常需要同时保留原生镜像和 Nydus 镜像，构建流水线多出一个转换环节；安全扫描、镜像签名和准入策略等工具链，需要逐一验证能否识别转换后的产物——在合规要求严格的组织中，这一步甚至可能比运行时改造更耗时。

6.5　对内核版本的要求

RAFS v6 使用 fscache 时要求内核 ≥ 5.19。这只是入门门槛——failover、共享 daemon 等能力往往还需要更高版本，落地前要按发行版内核逐项确认。

旧内核可以退回 FUSE 模式，核心功能仍然可用，但 v6 相比 v5 的一项重要优势——元数据由内核解析、缓存命中时不再穿越用户态——就无法完全发挥。尤其要注意：不能用“顺序读取性能接近 loop device”的测试结果来说明 FUSE 模式的性能，因为这类结果通常来自 fscache 模式。

6.6　后端可达性 = 镜像可用性

传统 pull 有一个朴素的可靠性优势：镜像完整下载后，运行中的容器就不再依赖制品库。懒加载却把这种依赖延长到了整个容器生命周期。一个已经运行三天的训练任务，如果突然读取此前从未访问过的文件，仍可能需要通过网络从远端下载。

“

远端存储无法访问、blob 被误删、凭据过期或网络抖动，都可能让运行中的容器出现 input/output error。故障影响从“启动阶段”扩展到了“整个生命周期”——一次制品库抖动，可能同时影响大量已经运行数小时的训练任务。

因此，如果制品库和网络连接还不够可靠，就不宜贸然把懒加载用于关键训练任务。对 Nydus 来说，镜像存储服务已经从“启动时依赖”变成了“运行期依赖”。

6.7　两条路线的完整对照

维度 eStargz Nydus（RAFS v6）
格式本质 tar.gz 的可随机读扩展 专用只读 FS：bootstrap + chunk blobs
与 OCI 兼容 完全兼容，可退化全量拉取 非原生 OCI，必须有 Nydus 运行时

去重粒度 仅整层 digest 级 chunk 级；跨镜像需 chunk-dict

07

写在技术博客之外的话

到这里，技术账已经基本算清：Nydus 可以实现更多功能，但也增加了运行时组件和运维工作。但真正决定是否采用它的，往往不是某一项性能指标。

决定选型的，通常不是哪个技术更好，而是谁在为启动时间付钱。

7.1　被吐槽十年的 OCI，为什么还是主流

tar.gz 不擅长随机访问，社区对此抱怨已久。可它今天依然是默认选择，最重要的原因只有一个：

所有人都实现了它。

围绕“layer + digest”建立的工具链极其庞大：Harbor、Artifactory、ECR 等制品库，docker build、BuildKit、Kaniko 等构建工具，Trivy、Clair 等漏洞扫描工具，还有签名验签、准入控制、CI/CD、离线分发、灾备和审计系统。它们共享同一个基本假设：镜像由一组按 digest 寻址的层组成。

核心判断

一种格式的价值，不只在于设计是否优雅，还在于它是不是所有参与方的最大公约数。任何替代方案都需要与这条工具链逐环适配，参与方越多，协调成本就越高。

再回头看 eStargz 的“在旧格式里雕花”，就能理解这种选择并非保守，而是为了尽量少修改现有工具。它放弃一部分功能，换来制品库、扫描、签名等工具继续工作的可能性。这也解释了为什么这种方案虽然不如专用格式彻底，仍然会被广泛采用。

7.2　启动慢，对谁才是问题

对长时间运行的大规模训练来说，答案往往是否定的。一个任务要运行几天甚至几周，启动多花五分钟，占整个生命周期的比例可能微乎其微。这类场景更值得优先解决的，通常是训练稳定性、checkpoint 保存与恢复、通信效率以及故障恢复速度。

值得警惕

如果启动时间占比不到 1%，引入懒加载就可能增加许多运行时故障类型，却只能换取非常有限的时间收益。一次 blobcache 异常导致的训练中断，就可能抵消此前节省的全部启动时间。

但也有例外，它们的共同点是：启动成本会被次数放大。

Spot / 抢占式训练

被抢占一次就换一次节点，启动成本乘以抢占频率。

大集群的故障重调度

节点规模上去之后，“总有节点在故障”，重调度会成为常态。

调试和频繁发布版本

改一行代码就要重新运行一次，工程师会反复等待。

该看的不是单次启动多久，而是

启动时间 × 启动次数 ÷ 总运行时间

7.3　但 serverless 是另一个世界

如果把同一项技术放到 RunPod、Modal 这类 serverless GPU 平台上，结论可能完全相反。在那里，计费单位是秒，用户也会直接感受到每一秒的等待。从点击“运行”到服务可用之间的时间，无法像长时间训练那样在总运行时间中变得微不足道。冷启动 90 秒与冷启动 3 秒，带来的并不只是性能数字差异，而是截然不同的使用体验。

镜像在这里也不再只是“运行环境的一部分”，而是服务启动过程中的一个步骤。它与 CDN、网页加载时间属于同一类问题：延迟直接影响体验，体验又会影响用户是否继续使用产品。

训练集群

一个镜像可能在同一节点上连续运行一周，chunk 级去重和 blobcache 跨镜像复用的机会有限。

serverless 平台

同一节点一天内可能启动几十甚至上百个租户镜像，而它们往往共享 CUDA、PyTorch 和常用依赖。后启动的某个镜像，大部分 chunk 可能已经存在于本机 blobcache 中。

因此，对 serverless GPU 平台来说，镜像加速会直接影响服务能否在规定时间内启动。这也解释了为什么许多平台会自行开发或大幅修改懒加载方案：它们的服务方式几乎不允许较长的冷启动时间。

“

同一项技术，在长时间训练平台上可能收益有限，在 serverless 场景中却可能直接决定服务是否可用。差别不只在技术本身，还在于启动延迟是否计费，以及用户是否需要等待。

7.4　那到底怎么决定

先不要急着比较技术参数，回答下面三个问题：

1

启动时间占总运行时间多少？如果只占很小比例，应优先优化其他瓶颈。
2

不同镜像之间有多少相同内容？只有一两个镜像时，chunk 去重收益有限，eStargz 所需的修改较少；几十个镜像共享同一个基础镜像时，Nydus 才更容易节省大量空间和流量。
3

组织里是否有人长期维护这套系统？如果没有，应优先选择发生故障时仍能按普通镜像启动、并且团队更熟悉的方案。

保持诚实

本文中的倍数和趋势，都来自特定镜像、网络和后端条件。真正的收益必须先在少量测试节点上，用自己的镜像重新测量。阅读社区或厂商材料时，也要确认缓存是否已有数据、远端存储距离多远、读取方式是什么，不要把理想条件下的数字直接当作生产环境的预期。

08

小结
1

eStargz 是在旧格式里雕花，Nydus 则是重画一张图纸。前者继续以 layer 为压缩、寻址和叠加单位；后者把压缩与寻址细化到 chunk，把运行时文件系统视图提升到整个镜像。
2

新设计带来的收益：chunk 级去重、与层数无关的单一合并挂载、可选的内核态数据路径，以及更灵活的压缩算法。
3

对应的代价：许多工作从启动阶段转移到运行阶段——冷缓存首读更慢、常驻 daemon 带来生命周期问题、blobcache 需要单独管理、普通 OCI 运行时无法直接使用转换后的镜像，且容器运行期间持续依赖远端镜像存储。

技术之外，更重要的结论是：OCI 被广泛使用，不仅因为格式本身，还因为大量工具都支持它；替换方案最昂贵的部分，往往不是安装组件，而是学习新的维护和故障处理方法；启动慢对长时间训练可能无关紧要，对 serverless 却可能直接影响使用体验。

镜像懒加载从来不是一道
“哪项技术更先进”的单选题。

真正该问的是：你的业务是否足够需要它，
你的基础设施是否承受得起它，
你的团队是否维护得住它。
